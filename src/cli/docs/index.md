# qtcloud-feishu CLI 文档

`qtcloud-feishu`（量潮飞书云命令行工具）的设计说明与去向，写给将来接手操作这套系统的人。构建、用法、示例见 [README](../README.md)，开发方法见 [CONTRIBUTING](../CONTRIBUTING.md)。

## 目标

直接目标是让日常工作不走飞书客户端，全部从自己搭的平台走。这就是这里说的完全开放：操作入口在自己的平台，不受飞书客户端约束。

更大的目标是把组织流程做成可渐进自动化的数据结构：流程写成数据，执行者逐步从人换成系统，招聘是第一个试验场。平台层面的意图另有记录，见 [data/intention](../../../../../data/intention/index.md)。

## 三层，各说各的话

| 层 | 说什么 | 谁认识它 |
| --- | --- | --- |
| 流程（`recruitment.yaml`） | 状态、迁移、检查、动作——检查与动作写**定义的名字** | 执行器照着调 |
| 定义（`定义.yaml`） | 我们的话 → 一串飞书活动（`看谁进群了` = 一步 `im_chat_members`） | 串联器照着展开 |
| 基础单元（`src/resources/`） | 飞书有什么、怎么取（十三个动作、命令、参数、落盘名） | 后端照着拼命令行 |

这样分的好处是**不需要谁认识全部**：流程不认识飞书（换平台不改流程），基础单元不认识招聘
（换场景不改取数），中间的定义一个人读得完。三层都不写死值：定义与流程是配置，
飞书坐标走参数或环境变量。

## 设计哲学写在流程文件里

「流程是数据，不是代码」「人是当前实情，不是应有形态」「流程升级的方向就是把执行者从人换成系统」这几句话不在本目录，写在流程 YAML 的头部注释里——与实验室（`examples/quanttide-feishu-lab`）同一份配置，两边跑出相同的推进序列（见 CONTRIBUTING 的对照办法）。

注释是为交接预埋的：等别人接手，打开 YAML 就能直接读到这套系统的设计哲学和当前边界。本目录不复述注释，改流程时直接读原文。

## 当前形态与目标形态

当前形态是单作者验证期：命令行三个子命令（`unit` / `define` / `flow`）已经能跑，流程与定义都是
外部配置，基础单元可对着假 lark-cli 或真 lark-cli 跑——差的是真飞书那一侧的资源位置、权限与
字段解析（如群成员真 CLI 返回 open_id，取邮箱要补一步）。

目标形态是多用户：作者之外，非技术的操作者在这套系统里日常推进流程。

接真飞书之前先验证结构与执行器本身：同一份流程与定义，实验室（Python）与本 CLI（Rust）跑出
相同输出——推进序列与状态文件逐字节一致。跨语言对照验证的就是「配置 + 通用执行器 + 基础单元」
这套架构不依赖具体语言。
