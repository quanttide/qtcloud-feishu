## 阶段二：待确认队列接真数据 —— 已完成（2026-10-29）

- 达成标志：打开 Studio 能看到真实草稿卡片（收件人、主题、落盘时间）；三种状态分清——数据源没接上 / 队列为空 / 有草稿；字段缺失与读取问题原样报出。
- 数据通路选择：**桌面版直读 XDG 目录**（零新增设施、同库同状态）；web 形态读不了本地目录，上云时把 `DraftSource` 换成服务封装，对外形状（`DraftLoad`）不变。读取异常统一按「数据源没接上」呈现，不白屏。
- 遗留：按钮仍禁用（确认写回是阶段三）；演示数据在 `~/.local/state/qtcloud-feishu/演示.json`，真实流程跑起来后可删。

范围（已完成）：

1. ~~数据通路二选一~~：定桌面直读，见上。
2. ~~`Draft` 模型重对齐~~：`PendingDraft` 字段对齐落盘——`draft_id`、`to`、`subject`、`body`、信封文件修改时间；信封只回草稿 id 时，`to`/`subject` 从 `ops.jsonl` 兑底；`body` 按隐私规则不进日志，信封没有就报缺，不猜。
3. ~~「已发未发」判法~~：state 文件里 `confirmed` 为空且 `artifacts.草稿id` 非空即待确认（`confirmed` 就是那个标记，不用对照 draft-send 目录）。

数据契约（CLI 阶段二已定，2026-10-29）：

- 待确认 = state 文件（`<state>/qtcloud-feishu/<流程名>.json`）里 `confirmed` 为空且 `artifacts.草稿id` 非空的条目
- 草稿内容（收件人、主题、正文）= `raw/mail/draft-create/<页序>.json` 信封里对应字段；信封只回草稿 id 时，`to`/`subject` 从 `ops.jsonl` 兑底（正文按隐私规则不进日志，缺就报）；平台字段名会变，以落盘为准，解析失败要报出来而不是猜
- 确认写回 = 置 `confirmed` 为当天日期 + `trail` 追加「已确认」，重复确认报错——与 CLI 的 `flow::confirm` 同一语义，不发明第二种

## 阶段三：确认写回

- 达成标志：在 Studio 点「确认发送」，下一次流程执行真把这封草稿发出去；驳回后草稿不再被发送。按钮从禁用变启用。
- 顺序依据：CLI 阶段二已把「确认」定形为状态变更（`flow::confirm`：置 `confirmed` + 轨迹追加）——Studio 写回走同一语义同一字段，不发明第二种。
- 后置代价：不做则闭环永远差最后一厘米：草稿看得见、发不出去，人还得回命令行。

## 阶段四：后续界面（顺序待阶段三后定）

流程看板（推格状态）、能力目录（从登记生成表单）。两者的读契约都是现成的（流程状态 JSON、资源登记），没有硬依赖，先后看使用反馈，不预排。
