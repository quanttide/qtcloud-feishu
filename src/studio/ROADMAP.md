# qtcloud-feishu Studio 路线图

Studio 的实施路线：阶段目标、顺序依据、后置代价。定位（与 CLI 共用文件契约、不实现第二套飞书调用）在仓根 README，不在这。

> 更新日期：2026-10-29

## 阶段一：骨架与起点页 —— 已完成（2026-10-29）

- 达成标志：Flutter 工程 + 待确认队列页面，v0.0.1 装到本机；测试与 analyze 绿。
- 遗留：`Draft` 模型是凭落盘契约的想象立的（见反思 1）；数据源未接，按钮禁用。

## 阶段二：待确认队列接真数据

- 达成标志：跑一次起草流程后，打开 Studio 能看到那条草稿（收件人、主题、正文、落盘时间）；「已发」的草稿不再出现在队列里。
- 顺序依据：CLI 阶段二（草稿确认闭环）把 draft_id 与落盘字段定死，本阶段照契约读——契约先行，界面跟着定，避免现在这样按想象的字段写代码再返工。
- 后置代价：不做则 Studio 永远只能演示空态；页面代码按错误字段越写越多，等接真数据时删得也多。

范围：

1. 数据通路二选一，判据写在下面反思 2：桌面版直读 XDG 目录，或 CLI 提供读接口。定哪条走哪条。
2. `Draft` 模型重对齐：以 `raw/mail/draft-create/0001.json` 的真实信封字段为准（`draft_id`、`to`、`subject`、`body`…），删掉想象字段。
3. 「已发未发」的判法：对照 `raw/mail/draft-send/` 里出现过的 draft_id，不出现在其中的即待确认。

数据契约（CLI 阶段二已定，2026-10-29）：

- 待确认 = state 文件（`<state>/qtcloud-feishu/<流程名>.json`）里 `confirmed` 为空且 `artifacts.草稿id` 非空的条目
- 草稿内容（收件人、主题、正文）= `raw/mail/draft-create/<页序>.json` 信封里对应字段；平台字段名会变，以落盘为准，解析失败要报出来而不是猜
- 确认写回 = 置 `confirmed` 为当天日期 + `trail` 追加「已确认」，重复确认报错——与 CLI 的 `flow::confirm` 同一语义，不发明第二种

## 阶段三：确认写回

- 达成标志：在 Studio 点「确认发送」，下一次流程执行真把这封草稿发出去；驳回后草稿不再被发送。按钮从禁用变启用。
- 顺序依据：依赖 CLI 阶段二把「确认」的机制定形（确认是动作还是状态变更）——写回方式必须与 CLI 同一种，Studio 不发明第二种确认。
- 后置代价：不做则闭环永远差最后一厘米：草稿看得见、发不出去，人还得回命令行。

## 阶段四：后续界面（顺序待阶段三后定）

流程看板（推格状态）、能力目录（从登记生成表单）。两者的读契约都是现成的（流程状态 JSON、资源登记），没有硬依赖，先后看使用反馈，不预排。

## 设计偏差反思（2026-10-29）

对照代码与文档逐条核过：

1. **`Draft` 模型没有对齐依据。** `lib/screens/draft_queue.dart` 的四个字段（action/recipient/body/recordedAt）是当时按「落盘契约的最小面」想象的；落盘信封里真实存在的是 `draft_id`、`to`、`subject`，`recipient` 这个词在 CLI 侧任何地方都没出现过。README 写着「字段以落盘为准」，代码却先立了字段——说一套做一套，阶段二要按真信封重对齐。
2. **「Studio 读 CLI 的 XDG 落盘目录」在 web 形态下不成立。** Studio 按惯例是 web 静态产物（qtcloud-connect 的 Studio 就部署成静态站），浏览器读不了 `~/.local/share`。能直读的只有桌面形态。本机验证恰好在 Linux 桌面跑通，把矛盾盖住了；部署上云那天必然撞上。阶段二必须先把通路二选一定死，再写读取代码。
3. **按钮禁用是诚实的，但空态文案没说实话。** 页面显示「没有待确认的草稿」，实际是「数据源没接」——用户分不清是真没草稿还是坏了（这次就被问了一次）。阶段二改成区分两种空态：没接上数据源 / 接上了但队列为空。
4. **确认写回没有第二种做法的余地，但差点有。** 现在按钮注释只说「写回方式随落盘契约一起定」，没说必须与 CLI 同一种。若各自发明，同一批草稿会出现两种确认语义。阶段三的判据已写死：跟 CLI 一种。
